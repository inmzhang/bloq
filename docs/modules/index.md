# Modules

Modules define reusable block graph components that can be composed into larger
surface code computations. Define a component once, then place instances of it
wherever that operation is needed. Each instance has its own geometry placement
and logical values, while sharing the same definition.

Reuse keeps repeated layouts consistent and makes larger graphs easier to build,
check, and understand. A component exposes a small named interface, so its caller
can connect operations without managing their internal block IDs or action names.
Definitions can contain other instances, allowing a circuit to be assembled at
several levels of detail.

A **definition** contains blocks, pipes, [actions](../graphs/actions.md), and its
public interface. An **instance** places that definition in a parent graph. The
parent connects quantum ports and passes classical results between instances.

The **root module**, named `main`, is the entry point for the complete
computation. It can contain its own blocks and actions as well as child
instances, and connects those children into the larger graph. Its quantum ports
define the computation's external inputs and outputs, and its classical outputs
expose named logical results. The other named definitions form its reusable
component library.

## Module structure

| Part | BLOG spelling | Purpose |
| --- | --- | --- |
| Definition | `module Stage { ... }` | Store a reusable block graph |
| Quantum port | `in q_in: data = 0` | Expose a logical boundary at a Port block |
| Classical input or output | `in basis`, `out bit = mz` | Receive or export a Boolean value |
| Instance | `child0: Stage @ [0, 0, 0]` | Place a definition in its parent |
| Quantum connection | `child0.q_out -> child1.q_in` | Join two quantum boundaries |
| Classical binding | `read.bit => cap.basis` | Supply a value to a child's classical input |

### Definitions

A definition owns its local blocks, pipes, actions, and interface. Its block
IDs and action names belong to that definition. Reusing it does not require
renaming those elements by hand. Each instance gives them a separate context.

A definition may also contain child instances. Definitions can be nested,
but cannot call themselves through a cycle.

### Quantum ports

A quantum interface names the Port blocks through which logical states enter
or leave a definition:

| Declaration | Meaning |
| --- | --- |
| `in q_in: data = 0` | Incoming logical state at Port block 0 |
| `out q_out: data = 2` | Outgoing logical state at Port block 2 |

The connection determines the patch face; the Port's role determines whether
the interface is an input or output. Explicit temporal roles are independent
of the past or future connection; `role=auto` infers the role from time.
Spatial Ports require an explicit role. A multiplex Port also retains the
stationary output described in [Blocks and Pipes](../graphs/concepts.md).

The parent must connect **every quantum port of each child instance exactly
once**. To expose a child port at the parent's interface, connect it to a parent
Port at the same position after rotation and translation, with the same input
or output direction and resource type. To compose children, connect an output
to an input of the same resource type. Their exposed neighboring blocks must
be adjacent with compatible faces; a Hadamard seam supplies a basis change.
Connections provide no automatic routing. The parent's public inputs and
outputs remain open to its caller.

The **resource type** is an annotation of a port's intended use. It does not
change the geometry or physical instructions generated by compilation.
`data` labels an ordinary logical wire; `ccz` labels a qubit of a three-qubit
$|CCZ\rangle$ resource. The
[CCZ teleportation example](../graphs/actions.md#ccz-gate-teleportation) declares
three inputs such as `in ccz_0: ccz = 3`, one for each resource qubit. The caller
supplies their joint state. Simulation and verification setups can use these
annotations to choose input states and expected logical behavior. Module
validation checks that connected ports have matching labels; the annotations
themselves do not prepare or certify the resource state.

### Classical inputs and outputs

A classical interface carries Boolean values.
`in basis` declares an input that the parent must supply.
`out bit = mz` exports a named measurement, while `out odd = m1 ^ m2`
exports an expression. Measurement values are corrected logical results, as
explained in [Actions](../graphs/actions.md#named-measurement).

The parent uses the public name, such as `read.bit`, rather than the child's
private measurement name `mz`. A binding such as `read.bit => cap.basis`
supplies that result to another instance. It creates a classical dependency
and does not add a pipe between patches.

Each required classical input binds once. Dependencies must remain acyclic,
and an executable root has no unresolved classical inputs. Composition also
rechecks named readouts against the quantum outputs that remain live after
connection.

### Instances and placement

An instance names its definition and gives its placement. For example,
`child1: Stage @ [0, 0, 1] rotate Z 180` rotates the definition about its own
origin, then translates it into the parent. For a local position $p$, the
parent position is

$$
p_{\mathrm{parent}} = R p + t.
$$

The transform applies to blocks, pipes, action targets, and interface positions.
Nested instances compose these transforms. The names `child0.q_in` and
`child1.q_in` identify different uses of the same public port.

Static definitions with default cube heights can rotate about any axis.
Definitions containing T, selective, walking, patch rotation, or custom height
blocks must preserve `+Z`. Y blocks permit coordinate half turns. The supported
orientation is checked across the complete nested definition.

### Quantum connections

The parent writes each quantum connection explicitly:

| Connection | Effect |
| --- | --- |
| `0 -> child0.q_in` | Replace the child's input Port with parent block 0 |
| `child0.q_out -> child1.q_in` | Remove the two child Ports and join their neighboring blocks |
| `child1.q_out -> 1` | Replace the child's output Port with parent block 1 |

Place the instances so the exposed boundaries are compatible. Directions,
resource types, face bases, and geometry must agree after transformation.
Connections add no automatic routing. An authored `-H>` connection supplies
a Hadamard basis change, with the corresponding endpoint frames.

Child action targets follow the instance's rotation and translation. Feedback
on a consumed Port transfers to the retained wire in its endpoint Pauli frame;
X and Z exchange when it crosses a Hadamard pipe. The compiler composes
measurement correlation surfaces across the seam, so feedback in `child0` can
flip a measurement in `child1` and create a dependency between their actions.
A child's public Boolean inputs are supplied through explicit classical bindings.

### Controlled-adder

A bulk stage of a controlled adder combines the gallery's CCZ-injected **AND**,
**MAJ** (majority), and **UMA** (unmajority and add) components, following the
arithmetic layouts in [Low et al., *A Denser Planar Surface Code*](https://arxiv.org/abs/2605.30455).
AND forms the temporary bit $i'_k = q \land i_k$. MAJ combines it with the
incoming carry $c_k$ and target bit $t_k$ to produce the outgoing carry
$c_{k+1}$. UMA uncomputes the temporary carry information and extracts the sum
bit `out_k`.

`main` places these definitions as `child0`, `child1`, and `child2`. The AND
output feeds MAJ, and four MAJ outputs feed UMA. The two Hadamard seams match
the components' endpoint Pauli frames. AND and MAJ each receive one supplied
$|CCZ\rangle$ state through three resource Ports.
